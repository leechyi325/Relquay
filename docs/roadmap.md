## 竞品调研：Agents Anywhere（2026-11-28）

来源为其公开 GitHub 仓库的 README、CHANGELOG 与 docs（Apache-2.0，约 3.8k star，最新 2.2.0 于 2026-11-14）。以下是页面上写明的事实，未亲自部署试用；页面没写的内容不做推测。

**定位差异。** 它是 Server + Connector + 多端客户端：手机经 Server（PostgreSQL + Redis）控制各工作机上的 Codex、Claude Code、DSH，并支持 Pi、Hermes 等更多智能体，有云端与自建两种形态。Relquay 是单机自建：手机直连一台服务器上的网关，不做账号体系和多机中继。这是取舍，不是缺口：我们没有云依赖、没有数据库，部署面更小。

**它做得好、值得借鉴的点：**

| 项目 | 它的做法 | Relquay 现状 |
|---|---|---|
| 草稿 | 切换会话后草稿和阅读位置保留 | 此前切换即丢；**0.4.10 已做**（每会话草稿，退出登录时清除） |
| 消息复制 | 复制文本、条目 ID、条目 JSON | 此前只有代码块可复制；**0.4.10 已做**（每条消息复制按钮） |
| 表格 | 表格卡片：复制、下载 CSV、全屏 | 此前无；**0.4.10 已做**复制表格（制表符分隔，可直接粘进表格软件） |
| 图片 | 点击放大、双指缩放、加载失败可重试 | 此前无；**0.4.10 已做**点击全屏、再点放大并可拖动、失败降级提示 |
| 会话缓存 | 内存缓存最近 5 个会话，切换即显示 | 已有（0.4.9，手机本地存储，重开 App 仍在） |
| 重连补齐 | 事件游标增量补齐，失败回退整页快照 | 已有（0.4.9 重连补齐 + 推送通道） |

**它的已知坑，对我们是提醒：**

- 流式输出时上翻阅读被拉回底部、"回到底部"按钮抖动，它修了两次。我们的"回到最新消息"按钮和 `away` 判断需要在真机流式输出时确认。
- 重连后丢消息、切换会话时消息串台，修了两轮。我们的补齐与推送通道已覆盖，但真机弱网下仍待验证。
- 长回复里的引用块含代码或公式时崩溃（Android）。我们的 Markdown 同样需要在真机上用这类内容回归。
- 发送结果未知的消息不能自动重发，否则重复执行。我们的队列已按此处理（出错暂停）。

**对 Server + Connector 技术栈的借鉴评估（2026-11-28）：**

- 整套架构（PostgreSQL、Redis、Connector 租约、中继）不借鉴：与"一台自己的服务器、零数据库、内容不经第三方"的定位冲突，维护成本远高于收益。
- 会话列表等变化提示的合并推送：已有（网关 `publish()` 以 250ms 合并，客户端只重新读取变化的主题），无需再做。
- 稳定的会话级事件序号：现状是 Claude 的游标每轮从 1 开始，重连靠"读最新一页历史"补齐，并用定时器判断新一轮是否开始。要让序号跨轮次稳定，网关必须自己为每个 Claude 会话保存事件日志并改写订阅语义，等于重做实时通道，而当前机制已经过测试和修复。暂不做；只有出现无法用现有补齐解决的丢消息问题时再评估。

**不打算跟进的：** 账号体系、团队管理、云端模型网关、多智能体插件市场、桌面客户端。这些属于它的产品方向，会显著增加部署与维护成本，不符合 Relquay "一台自己的服务器"的定位。
